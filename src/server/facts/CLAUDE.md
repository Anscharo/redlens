# Chat facts (auto-injected context)

A **fact** is a block of context the chat injects into a turn only when the turn calls for it — deterministic, pure code, no LLM call, no network, so a miss costs microseconds and injects nothing. The registry is `src/server/facts/registry.ts`; the contract is `facts/types.ts`. Today: glossary definitions, role dossiers (`facts/roles.ts` — for a defined role the question names, alias- and plural-tolerant: its Definitions entry, the role family's Article, every doc titled with the role, and any "The <role> for X is Y" assignment; built 2026-09-10 because ranked search never surfaced A.1.7.1 for the example question about Operational Facilitators), entity rows, concept censuses (up to 3 of 10, routed — see below), and app documentation (`facts/features.ts`, which reads the Features guide and also fires from the `/features` page). All of them ride ONE synthetic tool round in the transcript, so the verifier, quote-grounding, and citation checks consume whatever they inject as ordinary turn evidence. Triggering is **two lanes**. The deterministic one (regex signatures) fires on its own. The second, `facts/similarity.ts`, scores the question against the fact's `prototypes` with an on-device embedding (ternlight — WASM, ~2ms, no network) minus its similarity to shared atlas-question prototypes, and catches phrasings no regex anticipates ("show me around", "what should i try first?"). It is **suppressed** when the question names a real glossary term, entity, or doc title, or is small talk: the embedding scores question SHAPE, not subject — measured, `pnpm eval:facts --embed` — so deterministic atlas-vocabulary matching supplies the subject knowledge it lacks, and it does nearly all the work (166 of 184 non-product questions are stopped by the suppressors, 6 by the margin). The margin is **deliberately permissive** (default −0.05, the measured recall knee): injected context is read by a large model that can ignore what it doesn't need, so over-injecting costs ~2k discarded tokens while under-injecting can lose the answer. Held out: 25/28 product questions vs the regex lane's 6/28, at 5 false fires in 92 — ~130 wasted tokens per atlas turn, vs 2,000 on every turn if the guide were always injected. `CHAT_FACT_SIMILARITY=0` disables the lane for every consumer at once; `CHAT_FACT_SIMILARITY_MARGIN` moves the features lane's operating point. Facts whose match IS their extraction (glossary, entities — they must know WHICH row to inject) declare no `prototypes` and never use the registry's per-fact lane.

The census fact (`concepts-prefetch.ts`) is a **second, differently-shaped consumer** of the same similarity mechanism, not routed through the registry's `prototypes`/`semanticHit` plumbing: it's 1-of-10 ROUTING (which slug, if any, up to `MAX_CENSUSES`=3), which a single `prototypes` array can't express. `facts/similarity.ts` exports `rankPrototypeSets(question, Record<slug, string[]>, negatives)` for exactly this — one embed call scored against every slug's prototype set and one shared negative set, sorted by margin descending — and `concepts-prefetch.ts`'s `routeCensuses()` is the one function both production and the eval call, so they can never diverge on the routing rule. Its competing class is also different: a census question already names atlas vocabulary, so the shared `ATLAS_PROTOTYPES` suppressor (built for "atlas vs app") would stand it down on sight — `routeCensuses` uses its own `CENSUS_NEGATIVE_PROTOTYPES` ("specific document lookup", not "app question") and only small-talk suppression. Measured (`pnpm eval:census`, 202 labeled questions): regex alone routes 30% of natural paraphrases correctly; similarity lifts that to 86% at a **zero** false-fire rate — stricter than the features lane's zero-false-fire bar being merely aspirational, because a census false fire is cheap (373B for one summary, 1657B for three, vs ~8KB for the features guide) but a **real-traffic check mattered anyway**: a margin picked from the labeled corpus alone (~0.2) fired on 12 of 67 distinct real chat messages ("trace the governance path for an amendment", "generate 10 did-you-know blurbs") that the synthetic negative pool never produced — open-ended requests, not disguised document lookups. The shipped margin (`CHAT_CENSUS_SIMILARITY_MARGIN`, default 0.4) is the point where both the synthetic and real-traffic false-fire rates hit zero; re-run `pnpm eval:census` with `DATABASE_URL` set before trusting a lower one. Shares `CHAT_FACT_SIMILARITY` as its on/off kill switch.

A **third consumer** (2026-08-21) is the chat's model-tier router: `src/server/chat/complexity.ts`'s `looksComplex`, called from `model-router.ts`'s `routeTier` as a second lane behind the regex signals. Fire/no-fire like the features lane, but a third competing class again — "whole-corpus enumeration or synthesis" vs "one named subject". It exists because the STRONG regexes are high-precision and low-recall in a way their own bakeoff score hides: 11 of 14 on the bakeoff set is *in-sample* (the patterns were fitted to those questions), and against 28 natural paraphrases written to avoid every trigger they score **0**. Measured (`pnpm eval:complexity`, 180 questions): the lane adds 13 true positives for 1 false fire over regex alone, at margin `CHAT_COMPLEXITY_SIMILARITY_MARGIN` (default 0.25). **It deliberately does NOT suppress on `namesAtlasSubject`** — the suppressor that holds the features lane to 1 false fire in 184 stands this one down on 18 of 28 genuine positives, because whole-corpus questions are *made of* atlas vocabulary; naming a subject says a question isn't about the app, and says nothing about whether it's complex. Don't add it back. Zero false fires is unreachable here (one negative out-scores every positive), so the margin is set on the marginal trade, justified by an unusual cost asymmetry: a false fire routes to a model measured *better and faster* (2026-08-21 bakeoff, docs/chat-system.md §6.5), so it costs tokens, never correctness. Shares `CHAT_FACT_SIMILARITY` as its kill switch. **The real-traffic false-fire check that set the census margin has NOT been run for this lane** — watch PostHog's `chat_route_reason="similarity"` share, and run `pnpm eval:complexity` with `DATABASE_URL` set before lowering the margin.

A **fourth consumer** (2026-09-01) is the chat loop's *promised-tool guard*: `src/server/chat/announcement.ts`'s `announcesUnmadeToolCall`, called from `chat-loop.ts` at the point where a round's text would be accepted as the final answer. **It is the first to score an ANSWER rather than a question**, which changes the competing class again — not "another kind of question" but *an actual answer*, including the ones that correctly make no tool call at all. It exists because the loop's exit contract is "text + no usable tool calls = final answer", with one-shot guards for empty content and repetition but none for content that announces a lookup it never made: observed live 2026-08-20, an answer that read "One moment while I search the atlas." shipped as the turn's answer, badge-less (no claims ⇒ `computeOverall` degrades to `unverified`), and the user had to re-prompt. **The load-bearing suppressor is deterministic and runs first**: `isUncheckableAnswer` (verify/smalltalk.ts) means anything with a markdown link, figure or doc number in it is an answer and never reaches the embedding at all — which is what structurally protects the tool-free answers built from prefetch material, since the features fact requires app areas to be linked. Two further deviations from the siblings: the score is taken **per sentence, best sentence wins** (an announcement is a clause buried in pleasantries — the observed incident scores −0.41 whole-text and −0.03 on its best sentence), with a 20-character floor because shorter fragments are noise (a bare `"Answer."` scored 0.26, above the margin); and `isSmallTalk` is *not* used, because it classifies a user's greeting by word set and an assistant's greeting is a full sentence — greetings are a negative prototype class instead. Margin `CHAT_ANNOUNCEMENT_SIMILARITY_MARGIN` (default 0.25) is set at the **zero-false-fire** operating point, unlike the two permissive siblings: below 0.125 the false fires become product answers ("Searching the atlas is done from the search bar"), the exact class the guard must never touch. Retries are capped at one per turn and never fire on the final round. Shares `CHAT_FACT_SIMILARITY` as its kill switch (the regex lane survives it).

**Since 2026-09-22 one Jev request runs before the first token** (`chat/prefetch-judge.ts`, hard 600 ms cap, `CHAT_PREFETCH_JUDGE_MODEL=""` disables). It adds a third complexity lane (STRONG at P ≥ 0.58, alongside the two above), **replaces** the census similarity lane (regex ∪ Jev top-3 at P ≥ 0.60 — the similarity lane fired on 7 real messages with none correct), and filters the /teach shortlist. When the judgement is late or disabled, everything described above runs unchanged, so the similarity margins are now the fallback path. Details: docs/chat-system.md "Pre-first-token Jev judgement". Don't add a second pre-first-token call without asking.

**Add a fact by writing one and adding it to `FACTS` — never by editing `chat.ts`.** Every fact owns its own reader-facing copy (`summarize(count)`): the route emits a `facts` SSE event and a `recalling` status, so a fired fact shows up in the trace and the stage ticker instead of looking like the model just knowing things. `CHAT_PREFETCH=0` disables the whole registry.
