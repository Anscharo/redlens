# PAU state: admin-event history and live snapshots

Reads what the chain says about every contract in `src/data/pau-registry.json` (curation: the `pau-triage` skill, discovery: `pnpm pau:candidates`). An address the registry does not list is never read. The atlas is read for three things only: the RateLimitID hashes it states, which `probe.ts` reads live, the accounts it names to a vault's allocator and sentinel roles, which `targets.ts` asks the vault about, and the Integration accounts and mints its Solana instances state, which `svm-probe.ts` reads live (below).

**Behind is acceptable; wrong is not.** Every value stored is either read live or marked as what it is (the last value the history set, a unit inferred from size). Where a read fails or a fact depends on a guess, the reader says so rather than presenting it.

## Pieces

- `admin-events.ts` is the catalogue of governance events per (generation, role): role grants, `RateLimitDataSet`, per-pool parameters, diamond integrations, AdministeredAgent membership, BeamState's registrations, defaults and step limits. Facet events are listed under the diamond Controller, because facets run by delegatecall and the Controller emits them. Each generation lists the events its own controller source declares, with that source's arguments: the monolithic MainnetController's OTC events (`OTCBufferSet`, `OTCRechargeRateSet`, `OTCWhitelistedAssetSet`) take different arguments from the diamond OTCFacet's, so they have different topic0s, and the monolithic controller sets a Uniswap v4 pool's and an OTC exchange's max slippage through plain `MaxSlippageSet` (a v4 pool keyed by `address(uint160(uint256(poolId)))`), never `UniswapV4MaxSlippageSet` or `OTCMaxSlippageSet`. An event missing from a generation's list is never read for it. Operational events (relayer swaps, deposits, `RateLimitIncrease/DecreaseTriggered`) are left out on purpose: they are one per relayer action and say nothing about configuration.
- `sync-events.ts` fills `pau_events`. There is one `pau_cursor` per (chain, contract, event), because explorer log APIs filter on a single topic0 and that filter is what keeps the operational events out. A cursor at block 0 reads the contract's whole history, so backfill and catch-up are the same path. Each tick visits the least recently checked cursors until `PAU_EVENT_BUDGET_SECONDS` is spent. Reads stop `CONFIRMATIONS` blocks behind the head. A rate-limited explorer ends the tick for that chain only and leaves its cursor unmarked, so it is first in line next tick; any other error is written to `last_error` and the rotation moves on.
- `replay.ts` folds stored events into configuration: role holders (the monolithic AccessControl is not enumerable, so the replay is the only list), AdministeredAgent members (when each was added), every rate-limit key ever set, diamond integrations, the latest value per parameter and setting (`settingKey`: the subject, plus the asset for `OTCWhitelistedAssetSet`, which an exchange sets per asset). The change history keys "the value it replaced" the same way.
- `agent-live.ts` lists each AdministeredAgent set (actors, admins, grantors, revokers) live: the count, every index, and `getIsX` for each replayed member. A replayed member gets `holds` from the chain (null when the read failed, never false); a member the chain lists that the history lacks is added with `since: null` and marks the contract's `historyComplete` false, as `probe.ts` does for keys.
- `snapshot.ts` builds one deployment's `pau_state` row. It confirms each replayed holder with `hasRole` and reads every key with `getRateLimitData` / `getCurrentRateLimit`. A failed read is `null`, never `false`. Relayers and freezers have no events of their own; their roles show on the contracts that grant them.
- `beam.ts` reads what BeamState lets the Configurator (cBEAM) do to each RateLimits it manages without a spell. BeamState is a shared contract, one per chain (registry `shared`, role `beamState`; the `configurator` role's own events are origin evidence, read by `origin.ts`). A RateLimits gets a `beam` block only when BeamState registers it (`rateLimits(rl)`, else the replayed `AddRateLimits`/`DelRateLimits`): `getHop` and `getMaxChange`, and every default ("init") limit in force. Defaults are read live with `initRateLimits(key, rl)` and `initRateLimits(key, 0)` for every key the RateLimits holds or the replay names; this RateLimits' own default wins when non-zero, else the general one applies, as `getInitRateLimits` does. So a default shows even where BeamState's history is unread (no explorer serves Arbitrum without `ETHERSCAN_API_KEY`), except for a key the RateLimits has never held. A failed read falls back to the replay.
- Who can change a key, and whether the Operator can bring it to the atlas's value, is `src/lib/pauKeyRoutes.ts`: the atlas's Operator Execution rules (lower at any time; raise to at most the larger of the current value times `maxChange` and the key's default, a `hop` after the Operator's last raise of either field of that limit on that RateLimits, counted from the Operator changes in the change history; a limit locked as unlimited never moves), each reach citing the rule it rests on, in raw units only where the chain gave the key's token: a guessed scale would make the reach a guess. The chain's Configurator (registry `shared`, role `configurator`) is attached to each `beam` block when the steps are worked out (`value-steps.ts` `withConfigurators`), never stored, so a registry edit shows at once; its `DEFAULT_ADMIN_ROLE` on a RateLimits is the Operator's route, told apart from the spell-side admins. Whether a cBEAM is paired and the Configurator is running are not read, and the reader says so. A Solana limit (`src/lib/pauSvmRoutes.ts`) has no Operator route (no Configurator or BeamState): its admins are the holders of an active Default Admin Role Permission, read from the deployment's `permission` contracts (the limits' own contract holds no roles), and the route is a spell relayed to Solana through LayerZero governance, citing by UUID (`SVM_ROUTE_DOCS`, per prime) the Reserve's or Integration's setter, the Default Admin Role and the SubProxy's cross-chain whitelisting. Only the prime's known CPI authority (`SVM_ROUTE_DOCS` `authority`) is that route; any other active admin is named as able to set the limit directly, with no spell and no citation.
- An svm deployment (Keel's Solana ALM program, keel-fi/svm-alm-controller) emits no EVM logs: `svm-snapshot.ts` reads its listed accounts live over the chain's `solanaRpcUrl` (`svm-reader.ts`, ten a request through `politeFetch`; a failed batch fails the rebuild, which keeps the last snapshot) and decodes them at the program's known layouts (`svm-layout.ts`, which throws on any other size or discriminator, so an upgrade stops the read rather than mis-decoding it). Each Reserve's and Integration's limit becomes a rate limit keyed by its account's address on a `rateLimits` contract (the controller's state account), in the EVM controllers' terms (slope per second, rounded down, from the program's per day; `u64::MAX` as the uint256 maximum), counted in its mint's decimals (a Drift integration's mint is its spot market's). Each Permission is its own contract whose authority holds the role its flags grant while it is Active; the PAU values audit lists an atlas-stated one that is suspended as a role disagreement (`src/lib/pauAuditRoles.ts`). A stated Integration account, or the Reserve of a stated mint (derived from the controller and the mint), that does not exist is `unsetKeys` (a Reserve as `reserve:<mint>`). A stated address holding some other account is neither a limit nor unset, and only a 32-byte address is probed, so a wrong address in the atlas never stops the read; a listed member of an unknown layout, or an enum byte the layout has no name for, still does. The program accrues `available` only when an instruction touches the account, so the snapshot works out the amount available now from the stored amount, the slope and the last refresh (`lastUpdated`). The atlas side is `src/lib/pauSvm.ts`: keys keep the chain's case (every compare lowercases both sides), a symbol the instances state two mints for has none, a stated address that is not base58 names no account, and a title several accounts fit takes them all, so it reads ambiguous unless every one agrees. When each limit and Permission was last set comes from its configuration history (see "Solana configuration history").
- `units.ts` attaches the token each limit is counted in (`unit`), after derivation names the key. A unit is asserted only where the source of the generation holding the key says so:
  - monolithic (MainnetController, ForeignController and their libraries): fixed units (USDS for a mint or farm, USDC for CCTP or a Superstate subscription, an 18-decimal normalized value for Curve); the vault's `asset()` for an ERC-4626, ERC-7540, Maple or Spark Vault key; the adapter's `token()` for LayerZero, else the token itself; the token itself for Aave, PSM, asset-transfer and Uniswap V3 keys (UniswapV3Lib keys each token of a pool with its own amount), and for an Aave key also the aToken's `UNDERLYING_ASSET_ADDRESS()` as `unit.underlying` (absent when that read fails), which the instance cards check an Underlying Asset Address against;
  - diamond: a facet runs its own code, so a key gets a unit only from its facet getter's entry in `facet-keys.ts` (USDS, PSM and CCTP fixed; Basin in its asset; Uniswap V3 per-token keys in the token and aggregate keys in its 18-decimal normalized value; Aave in the underlying, read from the aToken for a withdrawal). The rule names the argument by role, not position.
  A key no rule covers, or one whose token's `decimals()` fails, has no `unit`, and readers fall back to `inferDecimals` and say so.
- `param-subjects.ts` names what each address-keyed parameter (`MaxSlippageSet`, `MaxExchangeRateSet`, a facet's) is set on: the subject's own `symbol()` and `decimals()` as `subjectToken`, and for an exchange rate the vault's `asset()` as `asset`, so a reader can show `spUSDC` and turn the 1e36-scaled rate into assets per share. A subject that answers no `decimals()` (an OTC exchange) gets neither. Whether a parameter is in use (a rate limit derived from its subject is non-zero) is read from the snapshot by `src/lib/pauParamUse.ts`; the PAUs page shows a guard only then.
- `targets.ts` reads what the pools and vaults a deployment's keys name answer about themselves, as `targets` by address: a Curve pool's `coins(i)` (from its `LIMIT_CURVE_*` keys, stopping at the first index that does not answer), and a vault's `owner()`, `curator()` and `guardian()` (from its `LIMIT_4626_*`/`LIMIT_7540_*` keys and exchange-rate parameters). A Morpho vault answers its allocator and sentinel roles only per account, so it is asked `isAllocator` / `isSentinel` for exactly the accounts the atlas names to them, read from `graph.json` by `role-claims.ts` (an instance's role params, against the vault its Token Address names). A target that answers nothing gets no entry. The instance cards check a Curve instance's underlying assets against the coins and a vault's role params against the rest (`src/lib/vaultRoleChecks.ts`); a single-holder role must be the first address its param states, because a curator's co-curators are listed after the holder.
- `probe.ts` reads every RateLimitID hash the atlas states (`graph.json`, by prime) live on each of that prime's RateLimits, for the keys its history has no event for. A key whose RateLimitData is all zero is recorded in `unsetKeys`; that, not a complete history, is what lets a reader say a key is not set (the Atlas vs contract check, and the reader's "Not set on any chain" hover card, `src/lib/pauKeyHolders.ts` `keyAbsence`). A key the contract holds that the history lacks marks the contract's `historyComplete` false.
- `atlas-inputs.ts` supplies the atlas artifacts a rebuild reads (`graph.json` for the probe, `addresses.atlas.json` for key derivation). The `pau` step is a tick step: it runs before the worker's build, and the worker image builds nothing, so `public/` holds neither on most ticks. It writes the copies published for the sha `sync_state` points at (`atlas_artifacts`) to a scratch directory, fetched once and only when a rebuild is due; a name the store lacks keeps its `public/` path, and one found nowhere is warned about. A graph that cannot be read probes no key (warned) rather than failing the rebuild.
- `store.ts` holds the refresh gate (every snapshot rebuilt once the oldest passes `PAU_REFRESH_SECONDS`, or when a deployment has none; snapshots of deployments the registry dropped are deleted; a deployment whose rebuild throws keeps its last snapshot and read time, warned by the worker, while the rest still rebuild, and a facet whose source the parser refuses leaves its keys unnamed rather than failing its diamond) and `GET /api/pau`, which attaches each contract's `atlasDocs` from the registry's atlas provenance as it serves (`src/lib/pauAtlasDocs.ts`), so a registry edit shows without a re-read, and serves the registry's `ignored` atlas claims as `rejectedClaims` for the PAU values audit report (`/reports/pau-audit`, `src/lib/pauAuditIndex.ts`). The weekly `pnpm census:pau` (`scripts/CLAUDE.md`) reads production's `GET /api/pau` to catch new disagreements between the atlas and these contracts.
- `rpc-sync.ts` and `rpc-cursor.ts` fill `pau_events` for chains read from HyperSync, or over JSON-RPC where no free explorer serves the chain; `handover.ts` says when the explorer path leaves a chain to them (see "Reading from HyperSync or JSON-RPC").
- `rpc-reader.ts` is the live reader (viem multicall per chain through `rpcFor`).
- `key-derive.ts` names rate-limit keys the atlas never writes out as a hash. A monolithic controller derives each key from a `LIMIT_*` constant (keccak256 of its name), alone or abi-encoded with an address, a CCTP domain or LayerZero endpoint id, or a `makeAssetDestinationKey` pair: an asset transfer's (asset, destination) or UniswapV3Lib's (token, pool), each marked `via` its second argument. The deriver hashes every zero-argument `LIMIT_*` view in the cached ABIs (`.cache/etherscan`, which `.dockerignore` keeps for the worker) against every candidate address, and the refresh stores the match as the key's `derived`. The candidates are the address artifacts, the registry, the naming material of the cached verified sources and of the spells `spell-sources.ts` stored (`source-material.ts`: every `keccak256("LIMIT_…")` name, `address … constant` and `bytes32 … constant`; Spark's spells carry an address registry naming L2 tokens, farms and transfer destinations the atlas never lists, and UniswapV4Lib's names and pool ids live only there), and the addresses the atlas has retired (below). A one-`bytes32` shape (UniswapV4Lib's `makeBytes32Key`) is enumerated over those words; the diamond passes none, so its bytes32 shapes still come only from hooks. Shapes are hashed lazily, cheapest first (`shapeDeriver`, shared with the diamond); about 11 µs a hash under Bun, so once any key is unnamed the full monolithic table costs about a minute and a half. `key-memo.ts` pays it only when the inputs change: each snapshot records `keysNamedWith` (a stamp of the constants, the candidate addresses and words, and `NAMER_VERSION`), and the next rebuild reuses its derivations, and, under the same stamp, its misses, so a steady-state rebuild hashes nothing. A diamond reuses only derivations from facets it still integrates and never its misses, because a hook's live reads also decide them. Raise `NAMER_VERSION` when a derivation change would name a key differently. Names the atlas states (the prime's and its instances' RateLimitID params) still come first wherever a key is shown.
- `spell-sources.ts` keeps the naming material of every spell behind a stored change in `pau_spell_sources`, because the worker's container starts without the explorer cache it fetched last run. It reads each `pau_tx_origin` spell and star spell, and every address a stored source declares as a spell or payload (`SPARK_SPELL`: a DssSpell that casts a prime's spell without a StarGuard names it only there), once each, from the explorer (`explorer-source.ts`); a spell no explorer has verified is asked again after seven days, and every spell is read again when `MATERIAL_VERSION` (`source-material.ts`) is raised. The worker step is `scripts/lib/worker-steps/pau-spell-sources.ts`, after `pau-origin` and at most 30 reads a tick. A lookup that fails for one spell is listed in the step's summary and stays queued while the tick reads on; only a rate limit, or a host cooling down after one, ends the tick; the `pau` step reads the stored material before naming, so a new spell names keys from the next rebuild on. An L2 payload a relayed action set runs is not read (no explorer every chain shares serves it), so a key only its payload names stays unnamed.
- `retired-addresses.ts` reads the worker's full atlas clone (`git log -p`, every file of every commit, about 4 seconds) for addresses some commit added and HEAD no longer holds anywhere, each with the commit after which no file held it. A key whose derivation takes one gets `retired` (address, date, commit) beside its `derived`: it meters an integration the atlas dropped, such as Grove's Centrifuge JAAA and JTRSY vaults. The mark sits on the row, not in the derivation `key-memo.ts` reuses, and is recomputed on every rebuild. The PAUs page leaves a retired key that is switched off out of its table and labels any other with the date; a retired key still on stays shown, since it can still move funds. When git fails the worker warns and marks nothing.
- `diamond-derive.ts` names keys by generation (`keyNamer`, the worker's entry). A diamond key is named only from the facets its Controller integrates now (the replayed `IntegrationSet`), never from the monolithic constants. `facet-source.ts` reads each facet's shapes from its cached verified source: its `_LIMIT_*` constants are internal (absent from the ABI) and its `…RateLimitKey` getters encode their arguments in RateLimitHelpers order, which is not the getter's parameter order, so only the source proves a shape. Anything it does not recognise throws. `facet-keys.ts` says, per getter, which argument identifies the instance (`via`) and the unit, and holds HOOKS: values the facet reads on chain to build a key (AaveFacet reads `POOL()` and `UNDERLYING_ASSET_ADDRESS()` from each aToken its `AaveMaxSlippageSet` names). A `derived` from a facet carries `roles`, `facet` and `getter`. Shapes of three or more addresses, a `bytes32` pool id or a Centrifuge id are hashed only from hook values; none has a hook yet.

The worker step is `scripts/lib/worker-steps/pau.mjs`. It injects `explorerLogs` (`scripts/lib/explorer-logs.ts`), `rpcHead` and `rpcChainReader`, so everything above is tested with fakes.

## Where a change came from

`GET /api/pau/history` lists every stored configuration change, one entry per transaction, each credited to what made it. A spell is named only where the chain proves it; anything else says what it is. The server builds the response once per change of its inputs (event count and head, origins resolved, archive entries checked), asking at most once a minute whether they moved, and gzips it once.

- `governance-events.ts` catalogues the events of the contracts that carry governance to a PAU, polled by the same cursors as the PAU's own (`admin-events.ts` lists them under every generation): a prime's StarGuard (`Plot`, `Exec`, `Drop`; registry role `starGuard`, one per prime on each Ethereum deployment), each L2 Executor (`ActionsSet*`; role `executor`, under `shared` per chain), the Configurator (`SetRateLimit`, `CallControllerAction`) and the Ethereum LayerZero Governance Sender (`GovernanceCallSent(guid)`; role `lzGovSender`, under `shared`). These are evidence, never entries, as are the Solana governance receipts (`LzReceive`, below).
- `casts.ts` fills `spell_casts` from DSPause's anonymous `exec` LogNote, whose caller is the spell, so every cast is known whoever sent the transaction (a keeper, TKGasStation, an EIP-7702 account). One cursor row; "not a cast" is said only for a block the cursor has passed.
- `origin.ts` runs `ORIGIN_RULES` in order and writes `pau_tx_origin`. The rules (`origin-rules.ts`, `origin-relay.ts`, `origin-direct.ts`):
  - StarGuard: `Exec(starSpell)` in the tx; the last `Plot(starSpell)` before it; the spell that cast in that Plot's tx.
  - Relay: `ActionsSetExecuted(id)` in the tx; its `ActionsSetQueued`; the Ethereum tx a bridge message id proves (`origin-links.ts`); that tx's spell by the two rules above. Without a proven id the change is `relayed`, with the action set and the Executor and no spell. A payload address is never a link: the same address recurs on other chains.
  - Cast: the tx is in `spell_casts`.
  - Operator: a Configurator event in the tx; the operator is the tx's target (the Safe), or its sender when it called the Configurator itself.
  - Solana (`origin-svm.ts`): see "Solana configuration history".
  - Otherwise a contract creation (`deployment`) or a `direct` call, read from the tx.
  Until every governance contract's cursors on the chain are read past the tx, it stays `unknown`; `unknown` and unproven relays are retried after six hours. The worker step is `scripts/lib/worker-steps/pau-origin.ts` (`PAU_ORIGIN_BUDGET_SECONDS`).
- `origin-links.ts` holds one entry per bridge (`BRIDGES`): OP-stack chains match the deposit tx's `sourceHash` against the portal's `TransactionDeposited` logs in the L1 block the L2 block's L1-info deposit names; Arbitrum follows the redeem's `ticketId` to the ticket's `requestId`, the Inbox's `InboxMessageDelivered` `messageNum`. A wrong address matches nothing rather than something wrong. Chains without an entry (LayerZero, CCTP, Orbit inboxes) get no link.
- `vote-archive.ts` titles spells older than the vote record from makerdao/community `governance/votes`, `EXECUTIVE_ARCHIVE_FILES_PER_TICK` files a tick (worker step `vote-archive.ts`), listing once. A file is `verified` only when its spell is in `spell_casts` and was cast on or after its date (`vote-archive-parse.ts`). A spell with no recorded cast is `rejected` only when its own contract says it never will be: `done()` false and `expiration()` past, or `done()` false with no `expiration()` (spells before mid-2020), said as such. Otherwise the file stays `pending`: a fetch failed, the spell is still castable, or it reports `done()` before the cast list holds its cast. It never touches `votes.json`.
- `history.ts` serves the history (`history-entries.ts` folds it): each change with the value it replaced, each spell with its executive from the vote record, else the verified archive, else the bare address.
- `history-queued.ts` adds `queued`: the governance steps stored events hold scheduled and not yet run, an Executor's `ActionsSetQueued` with no `ActionsSetExecuted`/`ActionsSetCanceled` of its id (with its execution time), a StarGuard's `Plot` with no later `Exec`/`Drop` of its star spell (with its deadline), and a LayerZero `GovernanceCallSent` whose guid no stored Solana receipt holds (`lz-message`), listed only once a pass has read receipts to the head and only from that window's start (an older message's receipt was never read). Which settings a step changes is not decoded. An Executor whose events are unread lists nothing, so an empty list is never "nothing queued".
- The reader's pending clock and the PAU values audit follow a disagreement link by link (`src/lib/pauPending.ts`; the spell steps in `src/lib/pauSpellStep.ts`, evidence in `src/lib/pauPendingEvidence.ts` and `src/lib/pauChainLed.ts`), worked out on the server: `GET /api/pau/steps` (`value-steps.ts`) builds every prime's value checks as the on-chain facts do, attaches each disagreement's step and who can change it from the document history, this change history, the vote record, the open atlas PRs and the Prime Snapshot polls (`src/server/prime-polls.ts`), and serves only that, keyed by `valueCheckId`, so a page fetches it only when it shows a disagreement. An input it cannot read is listed in `unread` and never read as empty: without the change history, the vote record or the document history no step is given, without the open PRs a change the chain made first says nothing, and without the polls a PR linked through one says nothing. Either side can move first, and the timestamps decide which did (`moveOrder`, the same rule the audit's groups use). When the atlas wrote the value after the chain last set the key, the change that wrote it (its diff adds it) is linked to its spell directly: a Prime proposal's PR through the Snapshot poll whose body links it, which an executive's Prime Agent Proxy Spells section links in turn (`VoteIndex.snapshots`); any other PR by the spell date its own title or bullet names (`HistoryEntry.spells`, `src/server/history/CLAUDE.md`), through that date's executive. A forum thread's slug date is the thread's, not the item's (a thread lists several items, artifact items are carried by no spell, an item can be re-proposed for another spell), so a PR that links only a thread gets no claim, and a passed poll no executive links whose thread names no spell gets none either. The step is pending while the poll is open, the executive is not filed (within the vote record's slip) or not cast (until expiry), or it is cast and its changes are within `READ_DAYS` of executing, or an action set is queued on the deployment's Executor between that spell's execution and the next spell's, until `READ_DAYS` past its execution time. That window, not a bridge message, ties a queued set to the spell, so it is the one link made by timing, and an overdue set stops counting. On Solana the relay is a LayerZero message, which has no queue there (the governance program runs it on delivery): the step is pending (`queued`, `via` "layerzero", at the Ethereum transaction that sent it) while a `lz-message` sent in that same window is not received, until `READ_DAYS` after it was sent. The sender's event names only the guid, so an undelivered message to another chain counts too, for those days. A spell sets a Solana limit when its change touches the limit's own account (the key; `keySetBy`). Else the spell set the key to another value, executed without setting it, or never carried it, or the item is off-spell (an artifact or Sky Core poll, Grove's tagged items or Spark's SAEP edits) or its poll failed. A spell that had executed before the edit merged, by full timestamp, is one the edit records (`recorded`), so a disagreement there is the atlas's. When the chain set the key after the atlas last wrote the value: the key's last change in this history says who made it (a spell and its executive, the Operator), a merged PR belonging to that spell that edited the document without the value says the atlas passed it by, and an open atlas PR belonging to it is the atlas update still to come (the clock).

## PR environments copy instead of reading

A Railway PR environment (`redlens-pr-<n>`, `src/server/pr-env/gate.ts`) never reads an explorer or an RPC: the `pau` step and the `sync:pau-rpc` tail are skipped there with the rest of `--no-fetch`. Its worker's `pr-env-copy` tick step copies the tables in `src/server/pr-env/copy-tables.ts` (`pau_state`, `pau_events`, `pau_cursor`, `pau_rpc_cursor`, `pau_svm_cursor`, `chain_state`, the change-history tables `spell_casts`, `pau_tx_origin` and `executive_archive`, the spells' naming material `pau_spell_sources`, and the balance, bytecode and contract-state columns of `atlas_addresses`) from `PR_ENV_SOURCE_DATABASE_URL`, the development database, once (`src/server/pr-env/copy.ts`). A table is copied only while the PR environment holds none of its data (for a merge entry, no row with its columns set); once every table is seeded the step does nothing and never opens the source. Emptying a table there copies it again.

- The source is read inside one `REPEATABLE READ, READ ONLY` transaction, so every table comes from one snapshot, and each table under its own savepoint, so one that fails to read leaves the rest. The source login must be a read-only role, and the copy refuses one that can write a copied table (`scripts/CLAUDE.md`, "PR environments").
- An empty source table is skipped, so a truncated or half-migrated source never blanks this environment's rows.
- Each table is replaced in one transaction of its own. A `merge` entry instead overwrites its columns on the rows that match its key, because `sync.ts` owns those rows.
- Rows travel as `to_jsonb` and land through `jsonb_populate_recordset`, so jsonb stays an object and timestamptz keeps its microseconds.
- A table missing on either side is skipped with a log line. An unset or unreachable source is one warning, and the environment keeps what it has.
- A new PAU table is one appended line in `copy-tables.ts`.
- `copy.test.ts` uses a fake. Re-verify against real Postgres after changing the copy: create two scratch databases, run `bun src/server/migrate.ts` against each, seed the source, run `copyFromSource`, and compare `count(*)`, `jsonb_typeof` of every jsonb column and an md5 of `string_agg(row::text ORDER BY row::text)` per table.

## Why logs come from an explorer

With `ENVIO_API_TOKEN` set, every chain the chain registry flags `hypersync` is read from HyperSync instead (see "Reading from HyperSync or JSON-RPC"), which leaves only xlayer on an explorer. This section and its table describe the explorer path: xlayer always, and every chain when the token is unset.

Public RPCs cap `eth_getLogs` at about 10,000 blocks (Arbitrum's refuses even 1,000), far below a contract's lifetime. The explorer pages by result count instead.

`explorerLogs` tries the providers `explorerBases` lists, in order: Etherscan v2 (with `ETHERSCAN_API_KEY`), Routescan (registry `routescan: true`), then the chain's Blockscout (registry `blockscoutApi`). Every request asks for a 1,000-log page, because Routescan's default page is 100 and a short page reads as the end of the history. When Etherscan answers that the key's plan does not cover the chain, the fetcher moves to the next provider and skips Etherscan for that chain until the process ends. The worker is a cron process that exits after each run, so a change to `ETHERSCAN_API_KEY` takes effect on the next worker run. Any other error goes to `sync-events.ts` unchanged. A rate limit is not a refusal, so the cursor waits for the next tick and the fetcher does not try Routescan or Blockscout. Every PAU request (explorers, JSON-RPC, the live reader, the archive) goes through `src/lib/upstreamBackoff.ts`, so a host that says slow down is left alone longer than it asks, by every caller. Each API host has its own request clock (`throttleExplorer` in `scripts/lib/explorer-api.ts`): 1 request a second by default, or the registry's longer `blockscoutIntervalMs`. `BLOCKSCOUT_API_KEY` goes only to instances under `blockscout.com`, because another host rejects a key it did not issue. A chain with no provider records `no explorer serves <chain>`; a chain whose every provider refused records `every explorer refused <chain> (…)` with each refusal.

## Reading from HyperSync or JSON-RPC

`rpc-sync.ts` crawls every chain that has a log source, run as the `sync:pau-rpc` worker tail (`src/server/sync-pau-rpc.ts`), not by `sync-events.ts`. `scripts/lib/log-sources.ts` picks the source: HyperSync (`scripts/lib/hypersync-logs.ts`) for a chain the registry flags `hypersync` once `ENVIO_API_TOKEN` is set, else the chain's `logsRpcs` (`scripts/lib/rpc-logs.ts`), else none. The worker's `pau` step passes the chains the crawl owns as `skipChains` (`handover.ts`), so the explorer path stops reading or marking their cursors:

- The crawl owns a chain it has a source for once no contract's explorer cursor is ahead of its crawl cursor; a missing crawl cursor counts as block 0. One query over both cursor tables answers it for every chain. Only contracts the registry still lists count, because a dropped contract keeps the explorer cursors it stopped at and never gets a crawl cursor.
- So a chain no explorer has read (Base, whose explorer cursors stay at 0, or any chain on a fresh database) is the crawl's at once, and a chain the explorer has read stays on the explorer until the crawl has read every one of its contracts at least as far. `historyComplete` reads the explorer's `pau_cursor` rows, which are already past block 0, so leaving the explorer earlier would show a history as read to the head while nothing read the chain.
- During the overlap both paths write the same `pau_events` rows (`ON CONFLICT DO NOTHING`), and `markRead` never moves a `pau_cursor` back (`GREATEST`), so the overlap costs only requests.
- A chain with no `pau_rpc_cursor` row starts its crawl at block 0 (HyperSync) or its deploy block (`logsRpcs`) and reads its whole history again. A chain that already has crawl cursors (Base, from mainnet.base.org) resumes from them when the token is set, because `eth_getLogs` answered every window it advanced past in full.
- Clearing the token gives a HyperSync chain back to the explorer on the next worker run, which resumes from its own cursors.

The crawl itself:

- One request names every contract and ORs every topic0, so it reads a block window for all of them. The crawl keeps one `pau_rpc_cursor` row per contract instead of one per event.
- A source answers for as much of a window as it reached, and the cursors advance only that far. `eth_getLogs` always answers the whole window; HyperSync scans until its time limit (about 10 seconds) and answers up to its `next_block`.
- A cold `logsRpcs` cursor finds its contract's deploy block by bisecting `eth_getCode`, about 26 requests. HyperSync has no `eth_getCode`, and skips blocks holding no match quickly, so its cursors start at block 0. Contracts at the same position share each window. A contract behind the others reads alone only up to the next contract's position, then joins them.
- `eth_getLogs` carries no timestamp, so each block that holds an event is read once with `eth_getBlockByNumber`. HyperSync returns those blocks' timestamps in the same answer; a log whose block comes without one throws rather than be stored with a wrong time.
- A contract the crawl reads from the start (no explorer has read it) keeps its `pau_cursor` rows at block 0 until its crawl reaches the confirmed head, so `historyComplete` reads false through the backfill. From then on each window that reaches the head marks them read.
- When the registry's events for a contract change, its crawl restarts at the deploy block, because a new event has no history read yet.
- Sources rotate per window. One that fails is left out for the rest of the run, and its error is stored on the cursors it was reading. A chain read from HyperSync has HyperSync as its only source.
- A failure other than a rate limit (a refused token, a dead endpoint, a contract with no code) is also written to the contract's `pau_cursor` rows, as the explorer path writes its own errors, so `historyComplete` reads false while the crawl is not reading; the next pass to the head clears it. A rate limit only delays the crawl, so it leaves them alone, as it does on the explorer path.
- Each run stops starting requests `PAU_RPC_DEADLINE_MS` after it starts (8 minutes by default, inside the worker's 11-minute tail budget). mainnet.base.org waits 1.334 seconds between requests (`intervalMs`), 75% of an assumed one request a second, because Base publishes no limit for it.
- Without HyperSync, Base is read from mainnet.base.org at 500 blocks a window: a cold backfill from its first registry contract is about 62,000 requests, roughly 23 hours of crawling, or about 34 hours of wall time at 8 minutes per 12-minute tick. Finding the 7 deploy blocks costs about 180 more requests, once. After that Base adds about 43,000 blocks a day, about 90 requests.

**HyperSync's limit is one budget for the token across every chain's host**: the free plan gives 15,000 units a minute and charges 1,000 a request, so about 15 requests a minute. `hypersync-logs.ts` starts requests at least 5.334 seconds apart on one clock for every chain (75% of that), and sends them through `politeFetch` with one `cooldownKey` for the account, so a refusal on one chain holds all of them. A 429's `x-ratelimit-reset` is the seconds until the window resets (`askedWait` tells that from GitHub's epoch seconds by size), and the wait is three times it. That is usually past the two-minute inline cap, so a 429 ends HyperSync for every chain for the rest of the run, and the next run resumes once the cooldown expires. A 503 is HyperSync's "queue full, not counted, retry": it is asked again after 10 and then 30 seconds before the source fails for the run (`BUSY_WAITS_MS`). One query usually spends HyperSync's whole time limit during a backfill, so a run makes about five requests a minute. A cold backfill of the whole registry measured, per chain: Ethereum 33 requests, Arbitrum 29, Base 70 (Base's dense blocks scan slowest, 200,000 to 700,000 blocks a query). Every configuration change production's `GET /api/pau/history` lists for a registry contract was in HyperSync's answer, on every flagged chain with history (Ethereum, Arbitrum, Avalanche, Optimism, Unichain, Robinhood, Plume, Plasma), and HyperSync found Base's, which production had not finished reading. Chains crawl one after another, so a cold start finishes over a few runs.

## Solana configuration history

History matters only for recent changes: a disagreement waits on a step for at most `PENDING_DAYS` (an executive's slip, its expiry, then `READ_DAYS`: 40 days), and an older change is past pending whichever side moved. So an svm program's history is a window that starts where HyperSync's Solana history starts (slot 391,000,000, 2026-01-03), never a backfill of the program's life.

- Every configuration change the program makes (to the controller, a Permission, a Reserve or an Integration) is emitted as an inner `EmitEvent` instruction to the program itself, carrying the account's full state before and after. `svm-events.ts` decodes the four configuration variants and skips `AccountingEvent` (a relayer's operation) and `OracleUpdate`; an unknown variant or bytes that do not add up throw, so an upgrade stops the crawl.
- `svm-hypersync.ts` reads them from `solana.hypersync.xyz` (the program's successful inner calls with discriminator `00`, joined to their transactions' signatures and blocks' times) through `hypersyncCall`, the EVM crawl's request path, so both spend one budget on one clock and one cooldown. Solana's `/height` answers a bare number. A query below HyperSync's history answers empty with no error, so a cold cursor first bisects all-blocks queries (about 30 requests, once) for the first slot it holds: those make no progress below it.
- `svm-sync.ts` is the crawl, run in the `sync:pau-rpc` tail after the EVM chains, on their deadline. One `pau_svm_cursor` row per program (start slot and time, next slot, `reached_at`, `last_error`, and the registry controllers it stored for: a change re-reads from the start). Reads stop `SVM_CONFIRMATIONS` (150) slots behind the head. Rows go to `pau_events` like EVM events: `tx_hash` the signature, `log_index` the call's place among the transaction's `EmitEvent` calls, `block` the slot, `contract` the account changed (the controller for a `ControllerUpdate`), `args` `{ authority, old, new }` as jsonb objects. Only a controller the registry lists is stored; a change to an account of it the registry does not list yet (a new Integration or Permission) is listed under the controller's prime (`history-entries.ts` `ownerOf`). A failure other than a rate limit is stored on the cursor until a pass reaches the head.
- `svm-history.ts` turns the window into the snapshot's times. It is complete when its last pass reached the head within a day, it holds no error, and it starts at least `PENDING_DAYS` back; then every contract's `historyComplete` is true. A limit's `setAt` is its latest change of status, slope or maximum, and `changes` counts the window's; a limit with no change in a complete window is set before it (`SetAt.before`, the window's start, with no time or transaction), which `setOrder` (`src/lib/pauValueDate.ts`) and the audit read as the chain having moved before an atlas change inside the window. Against an atlas change older than the window the order is unknown: the value gets no step, and the audit lists it under "order unknown". A Permission's holder is held `since` its last change, or null when the window holds none.
- The same query reads every `LzReceive` of the chain's LayerZero governance programs (registry `shared`, role `lzGovernance`: the Sky LayerZero governance program `SKYGRik…`), whatever program the message calls (`d8` filter on the Anchor discriminator). `svm-receipts.ts` decodes LayerZero's `LzReceiveParams`: the source eid, the sending OApp, the path's nonce, the guid, and from the message the calling SubProxy and the target program; bytes that do not add up throw. Each is stored as an `LzReceive` row of the governance program with `log_index` -1, -2, … within its transaction, so it orders before the changes it ran and never takes their places. The cursor's `controllers` stamp holds the controllers and, after a `|`, the governance programs (`stampOf`), so adding one re-reads the window from its start.
- `GET /api/pau/history` lists these changes like EVM ones. Their origin (`SVM_RULE`, `origin-svm.ts`): governance reaches the program over LayerZero (a spell's SubProxy calls the Ethereum LayerZero Governance Sender, `0x27fc…9cca`, which emits `GovernanceCallSent(guid)`; on Solana `LzReceive` with the same guid runs the call as that SubProxy's CPI authority, Keel's `FDFsob…k7Zk`). A change in a transaction holding a receipt is the spell behind the Ethereum transaction whose `GovernanceCallSent` names the receipt's guid, by the Ethereum rules (StarGuard, cast), with path `layerzero` and the message as the `relay` (`via` "layerzero", the program as `executor`, the nonce as `actionsSet`, the guid as `messageId`, the SubProxy as `sender`); it is `relayed` with no spell while that send is unstored, and retried. Only a receipt whose message calls a listed ALM program counts: `LzReceive` is permissionless, so a signer can run a pending message for another program beside a change of its own. A change with no such receipt is a `direct` call signed by its `authority`. Nothing is decided until an svm cursor on the chain reads receipts and has read past the slot (`receiptsPast`; one is enough, since each query carries every governance program), so a row stored before receipts were read stays `unknown` until the re-read passes it. Matching was checked on mainnet: the three 2026-05-11 receipts' guids (nonces 3–5, to `SKYTAiJ…`) are the three `GovernanceCallSent` guids of Ethereum tx `0xb03f728b…`.
- A `GovernanceCallSent` is listed as queued (`lz-message`, `history-queued.ts`) only when it was sent inside the window receipts are read over and no later than the last pass that reached the head: a send the crawl could not have seen the receipt of stays "reading", so a stalled crawl never reads as a message not received. The history's cache version includes that pass time. The reader gives a Solana value no step at all while a contract of its deployment has `historyComplete` false (`withOnchain`).
- In HyperSync's window Keel's program changed configuration twice (2026-02-11, the Freezer suspending the Primary and Secondary relayers, signed by its authority `2gDBGy…BYnh`: `direct`), so every limit reads as set before the window. The sender has sent five messages in its life, none to the ALM program: the Keel SubProxy's call to it was whitelisted on 2026-01-15 (`CanCallTargetSet`, block 24,269,280) and has not been used.

## When to move off the worker step

The producer is a worker tick step because none of these hold. HyperSync is a source the worker reads, not an indexer: it keeps no state of ours. Moving to an indexer (Ponder, or a hosted one such as MultiBaas, Goldsky or Envio's HyperIndex, behind the same `pau_*` tables) is justified once any one does:

1. Values must be fresher than about a minute.
2. Operational (relayer) events must be indexed, not only configuration.
3. State has to be rebuilt by replaying every event, not read live.
4. The step takes more than a couple of minutes per tick, or the backfill cannot converge within the budget.
